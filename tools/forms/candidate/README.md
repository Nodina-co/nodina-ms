## Contrat testé

GET `?mode=token&locale=fr` ou `en` émet un UUID généré par le serveur, signé avec son heure, son expiration et sa langue. Il n’enregistre aucune demande. Le client l’obtient une fois et le réutilise pour tous les POST de cette tentative ; aucune nouvelle référence n’est obtenue automatiquement après un refus ou une expiration. GET sans mode rend un formulaire avec la même preuve dans des champs cachés ; le mode sans JavaScript conserve donc une référence stable pour son POST.

La durée doit être explicitement configurée entre 60 et 86400 secondes. Les 24 heures sont la proposition d’architecture, pas une durée adoptée par ces tests. La clé HMAC reste dans Script Properties et n’est jamais retournée dans une réponse ou un journal. La rotation de cette clé invalide les jetons encore en circulation ; ne pas la remplacer pendant une recette sans le prévoir.

POST accepte les champs et le consentement `contact-v1`, puis cherche la référence dans le seul dossier de l’application, y compris en corbeille. Même référence et même contenu : pas de second fichier ni de second envoi. Contenu différent, référence retirée ou jeton expiré : refus. Les opérations Drive et les helpers de retrait partagent le verrou du projet.

Avant une création non idempotente, Script Properties conserve un état minimal : référence, HMAC du contenu, timestamp, expiration et ID si connu. Aucun corps, e-mail ou nom dans cet état. Si le résultat de création est inconnu, une recherche ou l’ID connu permet de reprendre ; si aucun fichier ne peut être identifié, le traitement reste bloqué. Un état de création incertain ne disparaît pas automatiquement à l’expiration : réconciliation privée par JD nécessaire. La limite est de 100 opérations ouvertes ; aucun marqueur n’est évincé pour libérer une place.

Le contrôle propriétaire/permissions rejette les partages supplémentaires et les Shared drives. Les coordonnées ne sont écrites qu’après ce contrôle, dans Contact et dans aucun titre ou notification. Tous les champs visiteurs sont écrits avec RAW ; seule la formule D2 de Conservation, définie par le développeur, utilise USER_ENTERED avec les séparateurs points-virgules de la locale fr_FR. Dernier échange reste vide : réception ne signifie pas dernier échange confirmé.

La notification ne contient que le sujet fixe, la référence et le lien privé. L’état `unknown` est persisté avant MailApp ; une réponse d’envoi perdue ou l’échec d’enregistrement du statut final ne provoque pas de second envoi. Quota connu à zéro : `failed`. La réception peut rester confirmée sans notification ; JD doit traiter les statuts failed/unknown.

## Synthèse et lecteur

`ndRebuildSummary_` recalcule les comptes depuis les fichiers conservés, sous verrou, avec pagination et vérification de la liste avant/après. Un fichier en cours d’écriture, dupliqué, retiré mais encore présent, illisible ou de schéma invalide rend la couverture indisponible. Les TEST sont exclus ; les jours sont calculés en Europe/Paris.
