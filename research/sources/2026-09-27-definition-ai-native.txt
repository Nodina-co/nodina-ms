## Ce que signifie AI-native pour NODINA

Pour NODINA, **AI-native ne signifie pas simplement utiliser l’IA**.

Une organisation, une équipe, un workflow ou un produit est AI-native lorsque l’IA est pensée comme une **capacité fondamentale du système dès sa conception**, et non comme une fonctionnalité ajoutée à un fonctionnement existant.

La distinction peut être résumée ainsi :

> **AI-native = concevoir les logiciels, les workflows et les équipes autour de l’IA comme une couche d’exécution fondamentale, en pensant humains, agents, modèles, mémoire, outils, evals et observabilité comme les composants d’un même système.**

Le test le plus simple est contre-factuel :

> **Si l’on retire l’IA, le système continue-t-il à fonctionner essentiellement de la même manière, simplement moins vite ?**

Si oui, il est probablement AI-assisted ou AI-enabled.

Si retirer l’IA remet en cause l’architecture, le workflow, la répartition des rôles ou le produit lui-même, on est beaucoup plus proche d’un système réellement AI-native.

---

## Le spectre : AI-assisted → AI-native

### AI-assisted

L’IA améliore ponctuellement le travail existant.

Exemples :
- un ingénieur utilise Copilot ;
- un commercial utilise ChatGPT pour rédiger un email ;
- un développeur demande ponctuellement du code à un LLM.

Le processus fondamental reste inchangé.

### AI-enabled

Une fonctionnalité IA est intégrée à un système existant.

Exemples :
- ajout d’un chatbot à un SaaS ;
- ajout d’un moteur RAG ;
- résumé automatique de documents ;
- génération de texte dans un produit existant.

L’IA apporte une nouvelle capacité, mais l’architecture métier reste essentiellement la même.

### AI-augmented

L’IA commence à modifier significativement certains processus.

Les utilisateurs délèguent davantage de travail à des modèles ou agents, mais les processus restent largement structurés autour du fonctionnement historique de l’organisation.

### AI-first

L’organisation privilégie systématiquement l’IA lorsqu’elle peut constituer le meilleur moyen d’exécution.

Les workflows commencent à être redessinés plutôt que simplement augmentés.

### AI-native

L’architecture, le workflow, les rôles humains, les agents, la mémoire, les outils, les mécanismes de contrôle et les métriques sont conçus ensemble autour de l’IA.

L’IA n’est plus une feature.

Elle fait partie de l’operating model.

# Les 7 principes de l’AI-native selon NODINA

## 1. AI is foundational

L’IA est un composant structurel du système.

Elle n’est pas simplement appelée ponctuellement depuis une application traditionnelle.

Le produit ou le workflow est conçu autour de ce qu’elle permet de faire.

---

## 2. Agentic by design

Les systèmes AI-native ne se limitent pas nécessairement au schéma :

**input → modèle → output**

Ils peuvent fonctionner selon des boucles :

**reason → act → observe → evaluate → continue**

Les agents peuvent utiliser des outils, rechercher de l’information, appeler des APIs, modifier des systèmes, vérifier leurs propres résultats et demander une validation humaine lorsque nécessaire.

---

## 3. Context is architecture

Dans un système logiciel traditionnel, l’architecture est principalement pensée autour du code, des données et des APIs.

Dans un système AI-native, le contexte devient également une composante architecturale fondamentale.

Cela comprend notamment :
- context engineering ;
- retrieval ;
- mémoire à court et long terme ;
- Company Brain ;
- permissions ;
- outils accessibles aux agents ;
- état du workflow ;
- historique des décisions ;
- sources de connaissance.

La qualité du contexte peut devenir aussi importante que la qualité du modèle utilisé.

---

## 4. Probabilistic systems require verification

Les systèmes IA sont partiellement probabilistes.

Ils nécessitent donc une couche explicite de contrôle et d’évaluation.

NODINA considère comme fondamentaux :
- evals ;
- tests automatisés ;
- tests E2E ;
- regression testing ;
- contrôles déterministes ;
- structured outputs ;
- guardrails ;
- validation humaine lorsque nécessaire.

L’objectif n’est pas de supposer que le modèle fonctionne.

L’objectif est de pouvoir mesurer quand il fonctionne, quand il échoue et comment son comportement évolue.

---

## 5. Observability is first-class

Un système agentique doit être observable.

Il faut pouvoir comprendre :
- quel modèle a été utilisé ;
- avec quel contexte ;
- quels outils ont été appelés ;
- quelles décisions ont été prises ;
- combien le workflow a coûté ;
- combien de temps il a pris ;
- où il a échoué ;
- quelles étapes ont été reprises ;
- quelle qualité de résultat a été obtenue.

Tracing, logging, evals, monitoring et versioning deviennent ainsi des composants de première classe.

---

## 6. Humans and AI have explicitly designed roles

AI-native ne signifie pas supprimer les humains.

Cela signifie concevoir explicitement la répartition du travail entre humains et systèmes IA.

Pour chaque étape, il faut déterminer :
- ce que l’IA peut faire seule ;
- ce qu’elle peut préparer ;
- ce qu’elle doit faire sous supervision ;
- ce qui doit rester humain ;
- quand une escalade est nécessaire ;
- qui conserve l’ownership final.

NODINA considère cette discipline comme du **Human–AI Systems Design**.

---

## 7. The organization itself adapts

Une organisation ne devient pas AI-native parce qu’elle déploie ChatGPT Enterprise.

Elle le devient lorsque ses processus, ses rôles, son architecture informationnelle et son operating model commencent à être redessinés autour des nouvelles capacités offertes par l’IA.

Cela peut modifier :
- la répartition des responsabilités ;
- le nombre de tâches pouvant être conduites en parallèle ;
- la structure des équipes ;
- les cycles de développement ;
- les processus de validation ;
- les métriques ;
- la documentation ;
- la circulation de la connaissance ;
- la gouvernance.

---

# AI-native Engineer

Pour NODINA, un AI-native engineer n’est pas simplement un bon développeur qui utilise Claude Code, Codex ou Copilot.

Il sait concevoir son travail autour d’agents.

Il maîtrise notamment :
- les coding agents ;
- le context engineering ;
- la décomposition des tâches pour des agents ;
- la parallélisation des flux de développement ;
- la validation du code généré ;
- les evals ;
- les tests ;
- l’observabilité ;
- les limites des modèles ;
- la gestion de plusieurs agents simultanément.

Il comprend que la rareté se déplace progressivement du code lui-même vers :
- le jugement ;
- l’architecture ;
- les spécifications ;
- la vérification ;
- l’orchestration ;
- la capacité à identifier ce qui doit réellement être construit.

---

# AI-native Team

Une équipe n’est pas AI-native simplement parce que chacun de ses membres utilise des assistants de code.

Son mode de fonctionnement doit lui-même évoluer.

Dans une équipe AI-native :
- plusieurs agents peuvent travailler simultanément pour chaque ingénieur ;
- la capacité brute d’exécution augmente fortement ;
- la vérification devient un bottleneck critique ;
- l’architecture et les interfaces entre tâches deviennent plus importantes ;
- la charge mentale doit être explicitement gérée ;
- la coordination humain-humain et humain-agent devient une compétence en soi.

Le rôle de l’ingénieur évolue :

**coder → spécifier → orchestrer → vérifier → décider**

Cela modifie également la notion de capacité d’une équipe.

On ne raisonne plus uniquement en nombre de développeurs, mais en combinaison de :
- capacité humaine ;
- capacité agentique ;
- niveau d’autonomie ;
- complexité du système ;
- bande passante de supervision ;
- charge cognitive.

---

# Collaboration et intelligence collective

Pour NODINA, l’excellence technique individuelle ne suffit pas.

Une équipe composée de profils exceptionnellement compétents ne fonctionne que si ces profils savent maîtriser leur ego et mettre leur expertise au service du collectif.

Un ingénieur NODINA doit être capable de :
- avoir conscience de ses compétences rares sans en faire un rapport de domination ;
- défendre une conviction technique fortement ;
- changer rapidement d’avis lorsqu’un meilleur argument apparaît ;
- demander de l’aide ;
- challenger un pair ;
- recevoir une critique ;
- partager le contexte et le crédit ;
- privilégier la performance de l’équipe à sa propre visibilité.

Cette **team intelligence** constitue une compétence à part entière.

# AI-native System

Un système AI-native peut combiner :

- modèles ;
- agents ;
- tools ;
- APIs ;
- mémoire ;
- Company Brain ;
- retrieval ;
- règles métier ;
- model orchestrator ;
- AI harness ;
- AI memory harness ;
- données ;
- observabilité ;
- evals ;
- guardrails ;
- human-in-the-loop.

Ces composants ne sont pas assemblés indépendamment.

Ils forment une architecture unique conçue autour d’un objectif métier.

Un système AI-native est donc moins un « logiciel avec de l’IA » qu’un **système socio-technique dans lequel humains et intelligences artificielles participent conjointement à l’exécution**.

---

# AI-native Workflow

Un workflow traditionnel ne devient pas AI-native simplement parce qu’une étape utilise un LLM.

L’approche NODINA consiste à repartir du résultat attendu.

Plutôt que :

**ancien workflow + IA**

on cherche :

**objectif métier → nouvelle architecture de workflow rendue possible par l’IA**

Cela peut supprimer, fusionner ou entièrement repenser certaines étapes historiques.

L’enjeu est donc moins :

> Où peut-on ajouter de l’IA ?

que :

> Si ce workflow était conçu aujourd’hui avec les capacités actuelles de l’IA, à quoi ressemblerait-il ?

---

# AI-native Organization

Une organisation réellement AI-native va encore plus loin.

Elle considère humains et systèmes IA comme deux catégories de capacité d’exécution qu’il faut orchestrer ensemble.

Cela transforme :
- les équipes ;
- les processus ;
- les outils ;
- la documentation ;
- la mémoire organisationnelle ;
- le management ;
- la gouvernance ;
- les systèmes de contrôle.

À terme, une partie de la capacité opérationnelle de l’entreprise peut être portée par des agents persistants, des Company Brains, des systèmes de mémoire et des workflows automatisés.

---

# Ce qui n’est pas AI-native

Les éléments suivants ne suffisent pas, seuls, à qualifier une organisation ou un produit d’AI-native :

- utiliser ChatGPT ;
- utiliser Claude Code ;
- utiliser Copilot ;
- intégrer une API LLM ;
- construire un chatbot ;
- faire du RAG ;
- ajouter un agent ;
- automatiser un workflow avec n8n ;
- avoir une équipe data science ;
- mettre en place quelques POC ;
- acheter ChatGPT Enterprise ;
- nommer un Chief AI Officer.

Ils peuvent constituer des briques d’une transformation AI-native.

Mais ils ne représentent pas la transformation elle-même.

---

# Conséquence pour le positionnement NODINA

NODINA ne doit pas être présentée comme une société qui « ajoute de l’IA » dans les entreprises.

Son expertise est de concevoir les **nouveaux systèmes d’exécution rendus possibles par l’IA**.

Cela s’applique aux deux offres :

### AI-native Teams

Constituer des équipes qui savent réellement travailler dans ce nouveau paradigme : humains, agents, orchestration, parallélisation, qualité, evals et software craftsmanship.

### AI Systems & Transformation

Redessiner les workflows et construire les systèmes nécessaires pour que l’entreprise puisse exploiter l’IA comme une nouvelle couche d’exécution.

La logique commune est donc :

**AI-native Engineer  
→ AI-native Team  
→ AI-native System  
→ AI-native Organization**

NODINA peut intervenir à chacun de ces niveaux.
